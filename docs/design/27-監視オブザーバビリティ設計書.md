## 3. メトリクス定義

### 3.1 インフラメトリクス

閾値付きで監視するインフラメトリクスは CloudWatch Alarms として定義しており、SSOT は `infra/lib/ops-stack.ts` / `infra/lib/dsql-stack.ts`（§4.1）。本書に閾値を複製しない。

### 3.2 アプリケーションメトリクス

| メトリクス | 取得方法 | 用途 |
|-----------|---------|------|
| API レスポンスタイム | ログ (durationMs) | パフォーマンス監視 |
| API エラー率 | ログ (status >= 500) | 障害検知 |
| 認証失敗率 | ログ ([AUTH] 失敗) | セキュリティ監視 |
| アカウントロックアウト | ログ ([AUTH] ロックアウト) | 不正アクセス検知 |

### 3.3 ビジネスメトリクス（OPS ダッシュボード）

| メトリクス | エンドポイント | 用途 |
|-----------|-------------|------|
| DAU (日次アクティブユーザー) | `/ops/api/analytics` | 利用状況 |
| 活動記録数/日 | `/ops/api/analytics` | エンゲージメント |
| サインアップ数 | `/ops/api/analytics` | 成長 |
| トライアル → 有料転換率 | `/ops/api/analytics` | 収益 |
| MRR (月次経常収益) | `/ops/api/analytics` | 収益 |
| チャーン率 | `/ops/api/analytics` | リテンション |

### 3.4 Activation Funnel イベント (#831)

サインアップから初回報酬体験までの 4 ステップを計測するイベント。
`analytics-service.ts` の `trackActivation*` ヘルパーで発火する。

| Step | イベント名 | 発火タイミング | 初回判定方式 |
|------|-----------|-------------|------------|
| 1 | `activation_signup_completed` | サインアップ + consent 記録成功時 | サインアップは本質的に 1 回のみ |
| 2 | `activation_first_child_added` | 子供登録成功時（テナント子供数 = 1） | アプリ層で `allChildren.length === 1` をガード |
| 3 | `activation_first_activity_completed` | 活動記録成功時（子供のログ数 = 1） | アプリ層で `activeCount === 1` をガード（子供単位）。テナント単位は集計層で dedup |
| 4 | `activation_first_reward_seen` | スタンプ獲得またはレベルアップ時 | 毎回発火。テナント初回判定は集計層で dedup |

> **設計判断**: Step 4 はアプリ層での初回判定に追加 DB クエリが必要であり、
> イベント頻度（スタンプ・レベルアップ）が低いため集計層 dedup で十分と判断した。

## 4. アラート設定

### 4.1 CloudWatch Alarms（OpsStack）

alarm 名・条件・閾値は `infra/lib/ops-stack.ts`（DSQL は `infra/lib/dsql-stack.ts`）、どの alarm がどこへ通知されるかは `infra/lib/ops-alert-policy.ts` が SSOT。本書に値を複製しない。監視の分担は [13-AWSサーバレスアーキテクチャ設計書 §3.4](13-AWSサーバレスアーキテクチャ設計書.md) を参照。

### 4.2 Discord 通知チャンネル

| チャンネル | 用途 | 通知内容 |
|-----------|------|---------|
| #アップデート | デプロイ完了 | PR マージ → デプロイ成功 |
| #不具合 | 障害通知 | ERROR/CRITICAL ログ |

### 4.3 通知エスカレーション

| レベル | 条件 | 通知先 | アクション |
|-------|------|--------|----------|
| INFO | 正常デプロイ | Discord #アップデート | ログ記録のみ |
| WARN | 閾値超過 | Discord #不具合 | 1時間以内に確認 |
| ERROR | サービス異常 | Discord #不具合 + メール | 即時対応 |
| CRITICAL | サービス停止 | Discord @everyone + メール + SNS | 即時復旧 |

## 8. インシデント対応

### 8.1 障害レベル定義

| レベル | 定義 | 目標復旧時間 |
|-------|------|------------|
| P1 (Critical) | サービス全停止 | 1時間以内 |
| P2 (High) | 主要機能停止 | 4時間以内 |
| P3 (Medium) | 一部機能低下 | 24時間以内 |
| P4 (Low) | 軽微な問題 | 次回リリース |

### 8.2 対応フロー

```
1. 検知（アラート受信 or ユーザー報告）
2. トリアージ（障害レベル判定）
3. 調査（CloudWatch Logs + メトリクス確認）
4. 対応（ロールバック or ホットフィックス）
5. 復旧確認（ヘルスチェック + 手動確認）
6. ポストモーテム（ADR として記録）
```
