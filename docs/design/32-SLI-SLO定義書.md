## 1. 設計背景

公開 SLA（[docs/operations/sla.md](../operations/sla.md) §3.2 = `site/sla.html`）は顧客に**月間可用性 99.5%** を約束している。約束した値を測っていなければ、達成しているかどうかを誰も答えられず、劣化にも気づけない。本書は「何を・どこで計算しているか」を定める。

## 2. 設計原則

- **計算できない SLI は定義しない。** 計測元は保持期間が月をまたぐものに限る（CloudFront アクセスログは保管 3 日のため使わない）
- **目標値の SSOT はコード。** 数値は `infra/lib/ops-stack.ts` の `SLO_TARGETS` にあり、dashboard の見出しに出る。本書は意味と根拠を書く

---

## 3. SLI

計測元はすべて Lambda Function URL の標準メトリクス（`AWS/Lambda`、`FunctionName` = 本番アプリ関数）。CloudFront が Lambda に回したリクエストが対象で、S3 から配る静的アセットと CloudFront 自体の障害は含まない（後者は alarm `ganbari-quest-cloudfront-5xx` が検知する）。

| SLI | 定義 | メトリクス |
|-----|------|-----------|
| 可用性 | `1 − 5xx 応答数 / 全リクエスト数`（4xx はクライアント起因として失敗に数えない） | `Url5xxCount` / `UrlRequestCount` |
| レイテンシ | Function URL が受け付けてから応答を返すまでの p50 / p95 / p99。コールドスタートを含む | `UrlRequestLatency` |

5xx エラー率は `100% − 可用性` と同じ値なので、独立した SLI にはしない。

---

## 4. SLO

目標値は `SLO_TARGETS`（`infra/lib/ops-stack.ts`）。

| SLO | 根拠 |
|-----|------|
| 可用性 | 公開 SLA と同じ値。個人開発の SaaS で 99.9% は過剰で、デプロイやメンテナンスに余裕を持たせる |
| レイテンシ p99 | Lambda のコールドスタートが 2〜3 秒かかるため、p99 はそれを許容する値にする |

**SLA との違い**: SLA は計画外ダウンタイムの**時間**で判定し、計画メンテナンスと依存先（AWS 等）の障害を除外する。SLO はリクエストの**件数**で計算し、除外をしない。SLO が目標を下回っても SLA 違反とは限らないが、SLO を満たしていれば当社起因の劣化は SLA の許容内に収まっている目安になる。

---

## 5. 計算と確認

- **計算**: CloudWatch dashboard `ganbari-quest-ops` の「SLO (30d)」行。直近 30 日で固定して集計する（閲覧時に dashboard の時間範囲を変えても値は変わらない）
- **エラーバジェット**: 可用性目標の残り（`100% − 目標`）が 30 日間に許される失敗リクエストの割合。消費率 = `(100% − 実績) ÷ (100% − 目標)`
- **確認のタイミング**: 定期レポートには載せていない。alarm が鳴ったとき・リリース前に dashboard で確認する

### 5.1 エラーバジェット消費時の判断

| 消費率 | 判断 |
|-------|----------|
| < 50% | 通常運用 |
| 50〜80% | リスクの高い変更は延期する |
| > 80% | 信頼性の改善を優先する |
| 100% 超過 | 原因を調べ、再発防止を入れるまで機能追加を止める |
