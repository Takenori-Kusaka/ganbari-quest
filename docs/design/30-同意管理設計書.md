## 1. 設計背景

がんばりクエストは子供のデータを扱うため、保護者の明示的な同意をサービス利用の前提にする。同意の取り方と記録の仕方を決めておかないと、次のことが起きる。

- **同意を経ずに登録が成立する経路が残る**。サインアップフォームのチェックボックスだけで止めていると、JavaScript を切った送信・直接の POST・Google でのログイン（フォームを通らない）で同意なしの利用者が生まれる
- **改定した規約に誰も同意していない状態になる**。利用規約やプライバシーポリシーを改定しても、既存の利用者は古い版への同意のまま使い続ける
- **同意したことを示せない**。いつ・どの版に・どの端末から同意したかが残っていないと、問い合わせや監査に答えられない

本書は、同意の種類・取得の経路・記録・再同意・撤回を定義する。

## 2. 設計原則

1. **同意の主体は保護者** — 子供のセッションには同意画面を出さない（プライバシーポリシー第 9 条「未成年者の取扱い」）。保護者が管理画面を開いた時点で同意を取る
2. **必須の同意はサーバ側で強制する** — クライアントの送信制御だけに頼らない。同意が揃わない送信はサーバが拒否する
3. **記録は追記だけ** — 個々の同意の記録を書き換えたり消したりしない。消えるのはアカウント削除（§7）で世帯ごと消すときだけである。最新の同意は記録日時で判定する
4. **画面に出した文書の版だけを記録する** — 既に最新版へ同意済みの種類を、表示していないのに「いま同意した」と記録しない

## 3. 同意の種別

同意の種類は `src/lib/server/auth/entities.ts` の `CONSENT_TYPES` が SSOT。版の値は `src/lib/server/services/consent-service.ts` の定数が SSOT で、本書には写さない。

| 種類（`type`） | 対象 | 版の定数 | 必須 |
|---------------|------|---------|------|
| `terms` | 利用規約（`site/terms.html`） | `CURRENT_TERMS_VERSION` | ✅ |
| `privacy` | プライバシーポリシー（`site/privacy.html`） | `CURRENT_PRIVACY_VERSION` | ✅ |
| `cross-border` | 海外への移転（個人情報保護法 28 条。示す内容はプライバシーポリシー第 10 条） | `CURRENT_CROSS_BORDER_VERSION`（プライバシーポリシーと同じ版） | ✅ |

- 版の値は各文書の「最終改定日」と一致させる。一致は `tests/unit/services/legal-doc-version-parity.test.ts` が検査する
- 子供のプロフィールを作るときに、追加の同意は取らない。子供のデータの扱いはプライバシーポリシー（第 9 条）に書き、サインアップ時の同意を根拠にする
- Cookie は機能に必須のものだけを使い（プライバシーポリシー第 7 条）、同意バナーは持たない
- メールの配信停止（`/unsubscribe/[token]`）と Web Push の許可は、本書の同意記録の対象外で、各機能の設定で扱う

## 4. 同意の取得

`AUTH_MODE=local`（NUC セルフホスト / `npm run dev`）では同意を取らない（`/consent` は `/` へ戻す）。以下は Cognito での運用を対象にする。

### 4.1 サインアップ（`src/routes/auth/signup/+page.server.ts`）

```
1. メールアドレス・パスワード・パスワード（確認）を入力
2. [✅] 利用規約に同意する
3. [✅] プライバシーポリシーに同意する
4. [✅] 海外への移転に同意する
5. 登録 → 確認コードの入力
6. 世帯（tenant）が決まった時点で 3 種の同意を記録 → ロールの着地先へ
```

- `signup` アクションは 3 つのチェックが揃わない送信を 400 で拒否する。確認コードの `confirm` アクションも、同意を引き継いでいない送信を拒否する
- 同意を記録できるのは世帯が決まった後（手順 6）だけである（`confirm` アクションの中で、確認コードの検証 → 自動ログイン → 世帯の解決の後に記録する）
- 手順 6 の後の行き先は次のとおり:
  - 記録できた → `landingForRole`（`src/lib/server/auth/post-login-landing.ts`）が決めるロールの着地先（保護者は `/admin`、子供は `/switch`）。料金ページから来てトライアルを自動開始したときは `?trialStarted=1` を付ける
  - 記録に失敗した → その場で `/consent` へ送り、§4.2 で同意を取り直す
  - 招待の受諾に失敗して世帯が決まらない → 記録しないまま `/auth/join` へ送る。世帯が決まった後のアクセスで §4.2 が同意を取る
  - 確認後の自動ログインに失敗した → `/auth/login?registered=true` へ送る。ログイン後のアクセスで §4.2 が同意を取る

### 4.2 同意画面 `/consent`（`src/hooks.server.ts` / `src/routes/consent/+page.server.ts`）

`src/hooks.server.ts` は、次のすべてを満たすリクエストで同意の状況を確かめ、最新版への同意が 1 種類でも欠けていれば `/consent` へ送る（302）。

- `AUTH_MODE=cognito` で、開発用の Cognito モードではない
- ログイン済みで世帯が決まっていて、role が `child` ではない（§2 原則 1）
- Stripe の決済完了の着地（`session_id` クエリ）ではない（決済の確認を先に済ませ、次の遷移で `/consent` へ送る）
- パスが `/consent` / `/legal/` / `/auth/` / `/api/` / `/_app/` / `/favicon` で始まらない

同意の判定は**世帯（`family_id`）単位**で行う。`checkConsent(tenantId)` は種類ごとに `findLatestConsent(tenantId, type)` で世帯の最新の記録を取り、記録した保護者（`user_id`）は判定に使わない。したがって、同じ世帯の別の保護者が最新版に同意済みであれば、本人には同意を求めない。

同意画面は、最新版に同意していない種類だけをチェックボックスで出す。3 つのチェックが揃わない送信は 400 で拒否し、揃えば**欠けていた種類だけ**を記録して `/admin` へ移る（§2 原則 4）。

この経路が、フォームを通らない登録（Google）・サインアップ時の記録の失敗・規約の改定（§6）の 3 つを拾う唯一の取得点である。

## 5. 同意の記録

記録は Aurora DSQL の `consents` 表に置く（定義は `src/lib/server/db/dsql/schema.ts`）。

| 列 | 内容 |
|----|------|
| `consent_id` | 記録の ID |
| `family_id` | 世帯（tenant） |
| `user_id` | 同意した保護者（`users.user_id`。IdP の sub ではない） |
| `type` | §3 の種類 |
| `version` | 同意した文書の版 |
| `consented_at` | 同意日時 |
| `ip_address` / `user_agent` | 同意した端末 |

- 個々の記録を更新・削除する手段は repo に持たない（§2 原則 3）。アカウント削除（§7）のときだけ、`deleteTenant`（`src/lib/server/db/dsql/auth-repo.ts`）が世帯の `families` / `memberships` / `invites` と同じトランザクションで、その世帯の記録をすべて消す
- `user_id` は誰が同意したかの記録で、同意の判定には使わない（判定は世帯単位、§4.2）
- 最新の同意は種類ごとに `consented_at` の降順で取る（版の文字列の大小には頼らない）
- `type` の許可値は DB の制約ではなく `recordConsent` が `CONSENT_TYPES` で検査する（DSQL は制約を後から足せないため）

## 6. 規約改定時の再同意

1. 文書を改定したら、`consent-service.ts` の版の定数を新しい改定日に上げる（§3 の parity test が上げ忘れを検出する）
2. `checkConsent` は種類ごとに最新の記録の版を定数と比べ、1 種類でも一致しなければ再同意が必要と判定する
3. 保護者は次のアクセスで §4.2 の `/consent` へ送られ、同意するまで管理画面を使えない（`/legal/` の文書は読める）
4. 同意画面は、前に同意したことがあるかどうかで見出しを「規約の更新」と「新規の同意」に切り替える

---

## 7. 同意の撤回

同意の撤回はアカウントの削除で行う。手順と猶予期間は [account-deletion-flow.md](account-deletion-flow.md) が SSOT。
